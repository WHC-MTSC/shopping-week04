# 쇼핑몰 시간당 작업량 예측 서비스 · Hourahead

**쇼핑몰 운영자가 매 정각까지 완료된 판매전표 이력으로 앞으로 한 시간의 작업량 단계(없음·보통·혼잡)를 예측해 업무 준비에 참고하는 서비스입니다.**

## 서비스 정의와 이번 구현 범위

| 항목 | 정의 |
|---|---|
| 사용자 | 시간별 판매 집계를 확인하고 업무 순서를 정하는 쇼핑몰 운영 담당자 |
| 사용 상황 | 매 정각, 직전 시간의 실제 판매전표 집계가 완료된 뒤 다음 한 시간의 준비 상태를 점검할 때 |
| 입력 | 예측 시작 정각 + 그 직전 168시간(7일)의 연속된 실제 양수 판매전표 건수 |
| 출력 | 목표 정각부터 다음 한 시간의 작업량 단계(없음·보통·혼잡)와 세 단계별 모델 확률 |
| 활용 | 예상 혼잡이면 대기 업무와 준비 상태를 점검하고, 예상 없음이면 정리 업무 계획에 참고 |
| 적용 범위 | 원본 영국 소매 데이터와 같은 시각·집계 체계를 사용하는 로컬 검증용 프로토타입 |
| 예측하지 않는 것 | 정확한 주문 건수, 상품 수량, 실제 처리 시간, 필요한 직원 수 |

현재는 **서비스 정의 → 기존 모델 검증 → API → 사용자 화면 → 입력·예측·사용자 정답 로그 수집**까지 구현했습니다. 사용자 정답은 실제 건수, 실제 작업량 단계, 예측 정오(T/F)를 구분합니다. 입력·예측을 고유 예측 ID로 기록하고 정답을 같은 ID에 연결합니다. 로그는 SQLite에 먼저 저장하며 **로컬 S3 모사 저장과 CloudWatch 스타일 로그 콘솔**로 AWS 없이 전체 흐름을 확인할 수 있습니다. 실제 S3 어댑터도 포함되어 있으며, 인증·버킷 설정 후 원격 전송합니다. 원격 CloudWatch Logs 전송은 현재 구현하지 않았습니다. 로컬 모사 화면과 `simulated` 상태는 실제 AWS 수집 성공을 뜻하지 않습니다.

## 사용자 화면

서버 실행 후 **http://127.0.0.1:8000/** 에서 사용합니다. 별도 프런트엔드 설치나 빌드 없이 FastAPI가 HTML/CSS/JavaScript를 함께 제공합니다.

1. **샘플로 시작하기**를 누르면 저장소의 과거 실제 이력과 예측 시작 시각을 불러옵니다. 자동으로 예측하거나 현재 시각 데이터인 것처럼 표시하지 않습니다.
2. 자신의 입력을 시험하려면 원본 집계 체계에 맞춘 **예측 시작 시각**을 지정하고 CSV를 선택하거나 내용을 붙여넣습니다.
3. **작업량 예측하기**를 누르면 기존 `/predict` 모델이 실제 계산한 단계, 확률, 대상 시간, 모델 버전이 표시됩니다. 그래프는 입력한 시간별 실제 건수입니다.
4. 입력을 수정하면 이전 예측 결과를 숨겨 새 입력에 대한 결과로 오해하지 않게 합니다. 누락 시간·중복·잘못된 건수는 화면과 API에서 검증하며, 연결 실패와 처리 중 상태를 표시합니다.
5. 대상 시간이 끝난 뒤 **실제 결과를 기록해 주세요**에서 실제 건수·실제 단계·T/F 중 하나를 선택해 정답을 저장합니다. 예측 ID로 나중에 다시 조회할 수 있고, 수정한 정답도 이전 이력을 보존합니다. **저장 상태 새로고침**으로 로컬 보관·전송 대기·로컬 모사 완료·실제 S3 완료를 구분해 확인합니다.

CSV는 UTF-8(BOM 허용), 첫 줄 `hour,count`, 이후 정확히 168행입니다. 시각은 `YYYY-MM-DDTHH:00:00` 또는 공백으로 구분한 같은 형식을 사용하며, 열은 따옴표 없이 작성합니다. 최대 크기는 1 MB입니다. **CSV 예시 다운로드**는 화면 샘플과 같은 데이터를 내려받습니다. 파일명에 대응하는 예측 시각을 표시합니다.

```csv
hour,count
2011-09-20T06:00:00,0
2011-09-20T07:00:00,0
```

위 두 행은 형식 설명이며, 실제 예측에는 168행이 모두 필요합니다. 브라우저 시간대가 한국이어도 입력 시각을 한국 시간이나 UTC로 변환하지 않습니다. 서버는 입력과 예측, 사용자 정답 및 전송 상태를 `runtime/events.sqlite3`에 기록합니다. 브라우저에는 마지막 예측 ID만 보관해 다시 조회할 수 있게 하며, 샘플은 `data_source=demo`로 구분합니다. 화면 자체는 외부 글꼴·분석 도구·CDN 없이 로컬 자산을 사용합니다.

## 로컬 로그 콘솔

AWS 권한 설정을 기다리지 않고 저장·조회를 확인하려면 아래 모드로 실행합니다.

```powershell
$env:WORKLOAD_LOG_BACKEND = 'local-s3'
$env:WORKLOAD_LOCAL_S3_ROOT = 'runtime/local-s3'
uv run --locked uvicorn workload.api:app --host 127.0.0.1 --port 8000
```

**http://127.0.0.1:8000/log-console** 에서 입력·예측·정답 이벤트를 필터/페이지별로 조회하고 원본 JSON을 확인합니다. 화면은 실제 로컬 기록을 읽으며, 모사 객체는 `runtime/local-s3/hourahead-local-logs/workload-events/` 아래에 저장합니다. 샘플 예측과 정답을 만들어 같은 `prediction_id`, 증가하는 피드백 `revision`을 확인할 수 있습니다.

자세한 사용법은 **[로컬 로그 콘솔 안내](docs/LOCAL_LOG_CONSOLE.md)**, 실제 AWS를 사용할 때 역할별로 필요한 권한은 **[AWS 권한 목록](docs/AWS_PERMISSIONS.md)**에 있습니다. 이 모드에는 AWS 계정·IAM 권한이 필요하지 않습니다.

## 피처와 라벨

라벨은 해당 시간의 `positive_sales_invoice_count`를 **없음(idle)=0건, 보통(normal)=1~9건, 혼잡(busy)=10건 이상**으로 변환합니다. 10건 기준은 기존 4주차 분석의 높은 작업량 구간을 따랐으며 실험 전에 고정했습니다. 실제 직원 수나 처리 시간을 측정한 기준은 아닙니다. API는 정확한 주문 건수 대신 이 세 단계를 예측합니다.

정각에 직전 시간 집계가 완료되어 있다는 가정으로 해당 정각부터 한 시간을 예측합니다. 입력은 목표 시각과 그 이전 **168시간의 연속된 실제 판매전표 건수**입니다. 운영 중에는 매시간 완료된 실제 집계를 새로 제공해야 하며, 예측값을 이력에 넣는 여러 시간 앞 예측은 평가하지 않았습니다.

학습과 API는 `workload/features.py`를 공유합니다. 시각·요일·주말 여부·월·과거 1/24/168시간 전 건수·이전 3/6/24/168시간 평균·전날/전주 같은 시각부터 3시간의 과거 평균·시간과 요일의 순환값·월중 날짜를 후보로 비교했습니다. 선택된 모델은 **확장 피처에서 월을 제외한 17개 피처**를 사용합니다. 목표 시간의 정답·매출·판매량 등 해당 시간이 끝나야 알 수 있는 정보는 넣지 않습니다.

## 성능과 선택 과정

원본 8,787행을 섞지 않고 기존과 같은 시간 경계의 60/20/20으로 나눴습니다. 제공 CSV 이전의 이력은 자체 검증할 수 없으므로 첫 168행은 이력 준비에만 사용합니다. 실제 학습 5,104행, 검증 1,757행, 마지막 평가 1,758행입니다.

| 구간 | 시작 | 끝 |
|---|---|---|
| 학습 | 2010-12-15 09:00 | 2011-07-16 00:00 |
| 검증 | 2011-07-16 01:00 | 2011-09-27 05:00 |
| 마지막 평가 | 2011-09-27 06:00 | 2011-12-09 11:00 |

건수 회귀 피처 4종과 작업량 분류 48개 후보를 검증 구간에서 비교했습니다. 회귀의 검증 ±2건 일치율은 86.91~88.67%였지만 정확한 건수 일치율은 69.55~70.75% 수준이었습니다. 이전 PR #1의 마지막 평가 ±2건 일치율도 82.37%였으므로 정확한 건수를 보장하는 서비스로 설명하지 않고, 운영 작업량 단계로 문제를 재정의했습니다.

처음 분류 비교에서는 전체 정확도 약 91%인 모델도 혼잡 재현율이 0%에 가까웠습니다. 따라서 클래스 가중치를 보정하고 월을 제외한 피처도 비교했습니다. **검증 macro F1을 우선하여 모델을 선택**하고 학습+검증으로 재학습한 뒤 마지막 평가를 수행했습니다. 선택 모델은 `extended_no_month-extra-14-balanced`이며 검증 정확도 88.39%, macro F1 0.7351입니다. 클래스별 가중치는 학습 데이터에서만 계산합니다.

| 마지막 평가 지표 | 선택 모델 | 전날 같은 시각 | 항상 없음 |
|---|---:|---:|---:|
| 세 단계 정확도 | **90.56%** | 75.88% | 63.99% |
| macro F1 | 0.8370 | 0.6568 | 0.2601 |
| balanced accuracy | 84.09% | 65.63% | 33.33% |
| 주문이 있는 시간 정확도 | **76.46%** | 54.03% | 0% |
| 혼잡 재현율 | **85.71%** | 61.13% | 0% |

**85% 목표는 전체 세 단계 분류 정확도에서 달성했습니다.** 모든 지표가 85%를 넘는다는 뜻은 아닙니다. 혼잡 정밀도는 73.93%, 보통 재현율은 68.07%라 혼잡 과대 예측과 보통 구간 오분류가 남아 있습니다. 전체 점수에는 없음 구간 63.99%가 영향을 줍니다. 검증에서 97% 이상인 후보는 없었으며, 누수를 막기 위해 시간 순서를 지키고 목표를 피처에서 제외하고 저장된 과거 피처를 실제 이력과 대조했습니다. 앞으로 97~99%가 나오면 라벨 경계 완화나 쉬운 시간대만의 평가 대신 누수·중복·클래스 분포부터 점검해야 합니다.

이 마지막 기간은 PR #1에서 이미 결과가 공개된 **역사적 벤치마크**입니다. 이번 모델 선택에는 사용하지 않았지만 완전히 새로운 전향적 검증으로 주장하지 않습니다. 결과를 본 뒤 다시 피처나 라벨을 튜닝하지 않았습니다. 실제 서비스 도입 전에는 새 점포·최근 데이터로 별도 검증해야 합니다.

전체 후보 지표는 `artifacts/validation.json`, 최종 지표는 `artifacts/metrics.json`, 시간별 예측은 `artifacts/test-predictions.csv`에 있습니다.

## 실행

[uv](https://docs.astral.sh/uv/)와 Python 3.12 이상을 사용합니다. 아래 명령은 저장소 루트에서 실행합니다. 의존성은 `uv.lock`으로 고정했습니다.

```bash
uv sync --locked
uv run --locked uvicorn workload.api:app --host 127.0.0.1 --port 8000
```

- `GET /health`: 모델 준비 상태와 버전
- `GET /`: 한국어 사용자 화면 (모바일·데스크톱)
- `GET /example`: 정답을 포함하지 않은 체험용 과거 입력 JSON (`ForecastRequest` 계약)
- `GET /metadata`: 전체 입력 벡터(`feature_names`)와 실제 트리 사용 피처(`used_feature_names`), 라벨·시각 규칙·사용 한계
- `POST /predict`: 단계·확률·모델 버전과 `prediction_id`, UTC `recorded_at`, `log_status` 반환
- `GET /predictions/{prediction_id}`: 원본 입력·예측·모델 정보와 최신 사용자 정답 조회
- `POST /predictions/{prediction_id}/feedback`: 실제 건수·실제 단계·T/F 정답 기록
- `GET /logging`: 선택한 저장 대상의 대기·완료·실패 후 재시도 상태
- `GET /log-console`: CloudWatch 스타일 로컬 로그 조회 화면
- `GET /logs`: 필터·페이지를 지원하는 원본 이벤트 JSON 목록
- `GET /docs`: OpenAPI 사용 예시

```bash
curl -H "Content-Type: application/json" --data-binary @examples/request.json http://127.0.0.1:8000/predict
```

`examples/response.json`은 모델 출력 핵심 필드 예시입니다. 실제 API는 실행마다 생성되는 `prediction_id`, `recorded_at`, `log_status`를 추가로 반환합니다. 확률은 보정되지 않은 앙상블 확률이며 예측의 보장된 신뢰도로 해석하면 안 됩니다.

시각은 원본 영국 소매 데이터의 **시간대 오프셋 없는 현지 시각** 형식을 사용합니다. `Z`, `+09:00` 같은 시간대가 포함된 시각은 거부합니다. 한국 서비스의 시간을 그대로 대입하면 안 되며 시간대와 집계 체계를 맞춘 데이터로 재학습해야 합니다. 목표 시각은 정확한 정각, 이력은 오름차순으로 목표 시각의 168시간 전부터 1시간 전까지여야 합니다. 음수·소수·문자열·불리언 건수, 빠진 시간·중복 시간·현재 시간의 정답·추가 필드는 422로 거부합니다. 건수는 0~100,000의 정수이며 이는 입력 보호 한도이지 학습 범위의 보장은 아닙니다.

모델은 시작할 때 한 번 읽습니다. `artifacts/model.json`은 구조를 검증한 JSON 트리 앙상블이며 pickle/joblib를 로드하지 않습니다. scikit-learn의 float32 입력 규칙을 동일하게 적용하며, 마지막 평가 전 행에서 JSON 모델과 원 모델의 확률 오차는 약 2.7e-15였습니다. 모델 파일이 없거나 유효하지 않으면 서버 시작이 실패합니다.

인증 없이 실행하는 로컬 개발 API입니다. 외부 공개 운영에는 예측 조회·정답 작성의 사용자별 접근 제어, 요청 크기 제한·관측·성능 검증을 별도로 적용해야 합니다. S3가 비공개여도 현재 API의 접근 제어를 대신하지 않습니다.

## 입력·예측·정답 로그와 S3

예측마다 원본 168시간 입력, 피처 벡터, 출력 단계·확률·모델 버전·모델 SHA-256을 기록합니다. 정답은 예측과 분리한 이벤트로 저장하며 `prediction_id`로 연결합니다. 모든 기록 시각은 UTC이고 모델 입력의 원본 현지 시각은 그대로 보존합니다.

| 정답 종류 | 입력 | 저장 의미 |
|---|---|---|
| `actual_count` | 0~100,000 정수 | 실제 건수에서 단계를 계산하고 예측과 비교 |
| `actual_stage` | `idle`, `normal`, `busy` | 실제 작업량 단계와 예측 비교 |
| `correctness` | JSON `true` 또는 `false` | 사용자의 예측 정오 판정; 실제 단계는 `null` |

T/F를 실제값이나 건수로 취급하지 않습니다. 정답 제출은 `submission_id` UUID로 중복을 방지하고, 수정은 새 UUID로 추가 기록합니다. 피드백의 `revision`은 예측별로 증가하므로 S3에서 가장 큰 revision을 최종 정답으로 사용할 수 있습니다. `POST /predict`의 선택적 `Idempotency-Key` UUID 헤더도 같은 요청의 중복 기록을 방지합니다. 같은 키를 다른 내용에 재사용하면 `409`입니다. `X-Data-Source: demo` 헤더로 과거 샘플을 구분합니다.

설정을 생략하고 S3 버킷도 지정하지 않으면 SQLite에 로컬 보관합니다. `WORKLOAD_LOG_BACKEND=local-s3`는 실제 JSON 객체 파일을 로컬에 생성합니다. 실제 AWS에는 `WORKLOAD_LOG_BACKEND=s3`와 `WORKLOAD_S3_BUCKET`을 지정합니다. 상태는 `local`(로컬 보관), `pending`(대기/재시도), `simulated`(모사 객체 저장 완료), `sent`(실제 S3 확인 완료)로 구분합니다. 로컬 저장이 실패하면 `503`으로 응답하며 저장 완료로 표시하지 않습니다. S3 전송은 이벤트별 JSON 객체를 사용하고 `IfNoneMatch="*"`로 같은 이벤트 키의 덮어쓰기를 막습니다.

서울 리전(`ap-northeast-2`)의 비공개 버킷 템플릿, 임시 로그인 인증, 최소 업로드 권한, 환경 변수, 실제 업로드 확인 방법은 **[AWS 설정 안내](docs/AWS_SETUP.md)**에 있습니다. 설정 항목은 [.env.example](.env.example)을 참고하세요. `.env`는 자동 로드하지 않습니다.

로컬 DB는 재시작 후 조회·정답 연결·미전송 복구에 필요합니다. 모사 완료와 실제 S3 완료는 별도로 관리하므로 `local-s3`에서 `s3`로 전환하면 같은 DB의 모사 기록도 실제 전송 대상이 됩니다. 시험용 기록 업로드를 원하지 않으면 새 운영 DB를 사용하세요. 이미 실제 S3로 전송한 후 실제 버킷/접두사를 바꿀 때는 같은 DB의 `sent` 기록이 새 목적지로 자동 복사되지 않습니다. 보관 중인 DB를 삭제하지 말고, 새 DB 또는 검증된 재내보내기 절차를 사용하세요. 현재 자동 삭제·보관 기간 정책은 없으며 사용량에 따른 저장·요청 비용과 보관 기간은 운영 시 결정해야 합니다.

## 재학습과 확인

```bash
uv run --locked python train.py
uv run --locked python train.py --evaluate-test
uv run --locked pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked basedpyright
node --test tests/input.test.mjs
```

첫 명령은 검증 결과만 생성합니다. 두 번째는 검증에서 선택한 모델을 학습+검증으로 재학습하고 모델 및 마지막 평가 결과를 생성합니다. `--evaluate-test`를 반복해 결과를 보고 모델을 고르는 방식은 새로운 검증 기간 없이 사용하면 안 됩니다. CI는 저장된 모델의 실제 벤치마크 예측 일치, API 계약, 입력 오류, 직렬화 검증과 코드 품질을 확인합니다.

Node.js 20 이상은 마지막 브라우저 입력 계약 테스트에만 필요하며 서비스 실행에는 필요하지 않습니다. 화면 샘플 → 실제 모델 응답 비교, 정적 자산 제공, CSV 시각·건수·누락·중복 검증도 자동 검사합니다. 로그 수집 테스트는 서버 재시작 후 기록 보존, 중복 요청·정답 수정, 잘못된 타입, S3 실패 후 재전송 및 AWS SDK 요청 계약을 검사합니다. 실제 AWS 업로드 검증은 인증된 계정의 원격 객체 확인이 별도로 필요합니다. 이번 서비스·로그 추가 작업에서는 모델을 재학습하거나 기존 평가 점수를 갱신하지 않았습니다.

## 자료 출처와 한계

`data/model-input.csv`는 2주차 `shopping-week02/result/model-input.csv`의 복사본입니다. 원본은 [UCI Online Retail](https://archive.ics.uci.edu/dataset/352/online+retail)의 2010~2011년 영국 소매 자료이며, 한 행은 연속된 한 시간 구간입니다. `positive_sales_invoice_count`는 양수 판매전표 수로 실제 상품 수량·처리 시간·직원 작업량과 동일하지 않습니다. 기존 집계 규칙에는 `BANK CHARGES` 전표 같은 항목도 포함될 수 있습니다. 이번 작업은 이 원본 정의를 유지했고 정답 및 과거 집계를 임의로 수정하지 않았습니다.

출처 SHA-256과 scikit-learn 버전, 분할 경계, 후보 설정, 평가 지표는 생성된 결과에 기록했습니다. 과거 데이터의 계절 변화와 작업량의 대리 지표라는 한계를 고려해 운영 준비의 참고용으로 사용해야 합니다.
